在 2026 年的第十届龙芯杯中，我十分荣幸地获得了个人赛一等奖。

本文回顾了本次个人赛参赛过程中的设计取舍、调试优化和经验教训，希望能为后续参赛者提供指导和参考。

## 简介

在本次参赛中，我的作品是一款基于 LA32R 子集的单发射六级乱序处理器核，代码见 [GitHub 仓库](https://github.com/skyhgzsh/loongsoncup2026)。

在复赛的四项测试中，该设计在 191.7 MHz 下约需 4310.6 万个周期，理论用时约 225 ms，
线下 FPGA 实测总用时为 229 ms；
但是由于时间和能力所限，该设计的稳定性仍有不足，未能通过 Alpha 测试中的 matrix。

在线下决赛中，通过快速修改设计中的 MUL 模块，其可以在 175 MHz 下以 12 ms 通过测试。

最终，尽管因 Alpha 测试未通过而被扣分，该设计仍获得个人赛一等奖，这也从侧面体现了其性能优势。

### `CPUCFG`

测试框架通过 `CPUCFG` 查询缓存配置，以决定是否执行缓存初始化与维护，使测试结果能够从内存中读出。

本设计采用写穿透、无写分配的数据缓存，不存在需要额外写回的脏行。
`ISA.svh` 将 `CPUCFG` 别名为结果恒为 `0` 的 `LU12I.W`，忽略查询索引；
测试程序会在执行时选择无缓存的初始化分支，并跳过对应测试后的缓存冲刷。

### 前端

本设计中的前端主要负责两部分，并据此对各项测试的 CPI 施加影响：
1. 单发射的指令供给决定了我们的 CPI 下限为 1；
2. 如果发生分支误预测，恢复需要 6 拍，指令流动需要 4 拍，总共 10 拍的惩罚。
   1. MATRIX loop1 的分支预测惩罚对应 loop2 最后一次迭代的退出；
   2. MATRIX loop2 对应 loop3 最后一次迭代的退出；
   3. MIXED stride 中的数据相关分支有 50% 的概率发生预测错误。

### 访存

访存对各项测试的CPI贡献同样分为三部分：

1. 带宽：ExtRAM 是单口 SRAM，一次访问固定占 3 拍。一个片段发出 N 次访问、只有 I 条指令可以重叠时，超出量为 max(0, 3N − I)。
   1. STREAM 的读写分属 BSE/EXT 两条通道、两个填充段请求稀疏，都能被完全藏住；
   2. MATRIX loop3 每轮 9 次访问（4 次 C 读 + 4 次写 + 1 次被抑制的 B 投机，27 拍）对 25 条指令，贡献 2 拍；
   3. MIXED stream 每轮 8 次访问（24 拍）只盖得住 16 条指令，贡献 8 拍。

2. 延迟：缺失 load 的 load-to-use 为 6 拍（SRAM 3 拍 + 响应与旁路 3 拍），若落在依赖链上就没有指令可填。
   1. MATRIX loop1 的 B 行每个 `k` 96 个字都是强制缺失（只在本 `k` 内复用），共泄漏 113 拍；
   2. CRYPTO crn 的两次 load 地址串行（第二次地址依赖第一次数据），每轮暴露 8 拍；
   3. MIXED stride 的索引 load 在循环携带链上，两条路径各暴露 5 拍。

3. 结构：LSU 只有一个请求槽，且每个 load 都会先无 tag 投机送 SRAM、查表命中后再撤销。
   1. MATRIX loop1 的 21 拍是每次 `k` 过渡的取指重启与序言/收尾摊销；
   2. MATRIX loop2 另记 2 拍过渡余量；
   3. MATRIX loop3 中 B 行命中的 4 连读会把请求槽与命中 FIFO 占住，使后续请求晚 4 拍到达控制器；store 组内还有 1 拍接受间隔——这 5 拍期间总线空闲，与带宽无关；
   4. MIXED stream 在 8 拍带宽之外还有 1 拍粒度余量（实测 25 = 24 + 1）。

## 设计

设计的整体架构如下图所示：

**图1：处理器核架构**

![处理器核架构](/cpu.drawio.svg)

如图所示，流水线分成前端、中端、执行、访存和写回。
主路径是 `IFU -> RAU -> RFU -> BPU -> XIU -> (MUL/LSU ->) WBU`。

### 前端

`IFU` 同时负责 `PC`更新和指令缓存。
本设计的指令缓存为直接映射的 2 行，每行 32 条指令，每条指令在填充时由 32 位压缩成内部的 29 位表示。

`CFG.svh` 中的 `PC_t` 仅保留字节地址的 `[22:2]`，`pc_ext()` 将其展开到 `0x1C000000` 起的 8 MiB BaseRAM/ExtRAM 区间。
`IFU` 中的 `PC` 会被切成四个子段，其作用如下：

**表3：`PC` 字段划分**

| 字段  | 范围    | 作用                                                    |
| ----- | ------- | ------------------------------------------------------- |
| `off` | [6:2]   | 与 `idx` 一起选择行内指令                               |
| `idx` | [7]     | 索引该行的 `tag` 与 `valid`                             |
| `tag` | [9:8]   | 与对应行保存的 `tag` 比较，未命中时填充整行             |
| `top` | [22:10] | 与两行共用的 `top` 比较，未命中时使两行失效并填充当前行 |

`IFU` 在 `RUNNING` 状态时，其完成如下操作：

1. 若本拍收到已寄存一拍的有效 flush，`PC` 换成 `flush_PC`，并清空送往 `RRU` 的两项缓冲。
2. 否则用当前 `PC` 的 `idx` 索引缓存，检查该行 `valid`、行 `tag` 匹配和共享 `top` 匹配三个条件。
   1. 若全部成立，视为缓存命中：预译码指令并尝试送入输出寄存器；握手成功后，`PC` 更新为预测的 `NPC`。
   2. 若有一项不成立，视为缓存缺失：锁存这次 miss 的 `top/tag/idx`，下一拍进入 `FILLING`。若 `top` 也不匹配，额外清除两行的 `valid`。

**表4：分支预测算法**

| 指令     | 预测 `NPC`       | 执行时的冲刷                 |
| -------- | ---------------- | ---------------------------- |
| `B` `BL` | 压缩时算好的目标 | 不冲刷；`BL` 另写 `PC + 4`   |
| `JIRL`   | `PC + 4`         | 一定冲刷到 `rj + offs`       |
| `BEQ`    | `PC + 4`         | 两源相等时冲刷到 `PC + offs` |
| `BNE`    | `PC + offs`      | 两源相等时冲刷到 `PC + 4`    |
| 其余     | `PC + 4`         | 不冲刷                       |

`BNE` 固定预测跳转，执行时只在两源相等、预测失败时纠正到顺序地址；`BEQ` 反之。

`FILLING` 通过 `LSU` 按握手逐字请求这一行的 32 条原始指令，收到后压缩成 29 位再写入；
32 个响应都到齐后回到 `RUNNING`。

填充期间若发生 flush，PC 和输出缓冲会更新，但已启动的行填充仍继续完成。

### 中端

`RRU` 内的 `RAU`、`RFU`、`BPU` 会依次对请求进行处理：

#### `RAU`

`RAU` 用 32 项 `RAT` 把架构寄存器换成物理寄存器，并从 16 项自由表 `FLT` 的头部给非 `r0` 目的分配 `prd`。
旧映射 `old_wd` 会随指令带走，并在退休时归还到自由表的尾部。

复位后初始化 `RAT[i]=i`，并将物理寄存器 32 到 47 放入自由表。

#### `RFU`

`RFU` 读 48 项物理寄存器堆。

若源 `prs == 0`，或该物理寄存器的发射状态等于写回状态时，则视为对应寄存器就绪；
否则记录生产者类型 `BypAlu`、`BypMul` 或 `BypLsu`。
`WBU` 退休缓冲头部的有效结果如果命中当前源，也会在这里直接旁路。
`PCADDU12I` 的第一源换成 `PC`，立即数指令的第二源换成扩展后的立即数。

零偏移存储指令可以从 `RFU` 直接进入 `LSU`，
但要求地址源就绪、LSU 快路径槽可接收，且 `RFU`、`BPU` 的 reg/skid 中没有更老的分支或访存指令。
如此旁路的指令不占用 `BPU` 发射槽，写数据以后由 `LSU` 自己捕获。

#### `BPU`

`BPU` 是最后一级旁路，它按源上保存的生产者类型，从 ALU、MUL、LSU 三条写回总线组合选出数据，
并在总线有效且 `prd` 与源物理寄存器号匹配时将源标为就绪，再把 `RRU_IXU_data` 同拍送给 `XIU`。

#### 冲刷

flush 先在 `XIU` 打一拍再广播。之后按 `RAU skid -> RAU reg -> RFU skid -> RFU reg -> BPU skid -> BPU reg` 从新到旧撤销：
恢复 `RAT`，归还 `prd`，恢复物理寄存器的状态和生产者。

已经由 `XIU` 握手发射的老指令继续执行，不在上述回滚范围内；
`WBU` 缓冲中的老结果也保留，只是在 flush 与回滚期间暂停退休。

### 执行

`XIU` 模块负责 ALU 运算、分支解析与访存地址计算，并将乘法和访存请求送往对应的下一级。
普通 ALU、MUL 和分支指令需要两源就绪；
访存指令只要求地址源就绪，store 的写数据可以稍后由 LSU 旁路捕获。

**表5：`XIU` 计算与发射**

| 指令类型    | 计算内容                                             | 目的模块                   |
| ----------- | ---------------------------------------------------- | -------------------------- |
| ALU 计算    | 加、减、与、或、异或、有符号比较、逻辑左移、逻辑右移 | `WBU` 写回                 |
| MUL 乘法    | 传递操作数                                           | `MUL`计算                  |
| LSU 访存    | 计算`rs1 + imm`作为访存地址                          | `LSU`访存                  |
| `B` `BL`    | 生成 `PC + 4`；仅 `BL` 将链接值写入 `r1`             | `WBU` 完成                 |
| `JIRL`      | 生成 `PC + 4` 链接值、`rs1 + offs` 跳转目标          | `WBU` 完成、`XIU_OUT` 冲刷 |
| `BEQ` `BNE` | 比较两源；相等时分别纠正到分支目标、`PC + 4`         | 必要时经 `XIU_OUT` 冲刷    |

`MUL` 模块只做 `MUL.W`，也就是计算两个数乘积的低 32 位。
它采用两级寄存器流水：`s0` 捕获操作数，`s1` 计算结果。
它把操作数拆成 18 位和 14 位的三路部分积，由三个 DSP48E1 计算，再用加法器拼出低 32 位。

### 访存

`LSU` 模块接收三类请求：`IFU` 的逐字行填充、`XIU` 的普通访存，以及 `RFU` 的旁路 store。
其按照地址高位将请求转发给对应模块：
对于访存，通过地址域 `addr[24:22]` 为 `000` 进 BaseRAM，`001` 进 ExtRAM，`111` 进 UART。
对于取值，请求只用 bit 22 区分 BaseRAM 与 ExtRAM。

普通访存首先进入统一请求槽。
经 `XIU` 发射且写数据未就绪的 store 可以移入两项 pending-store 队列，为后续 load 腾出请求槽；数据就绪后再按队列次序送回。
RFU 快路径 store 则保留在快路径槽和请求槽中等待，不采用同样的入队规则。三条写回总线会持续为这些等待中的 store 捕获数据。

`BSE` 是 BaseRAM 的 SRAM 控制器，同时处理取指和数据。
`EXT` 包含 ExtRAM 的 SRAM 控制器和其数据通路前的专用缓存 `EXT_CACHE`。
`URT` 是只实现软件用到的 16550 子集的 UART 控制器，覆盖数据、线路控制和状态口。

`EXT_CACHE` 是 16 KiB、4096 个 32 位字、每行一个字的直接映射写穿透缓存，只位于 ExtRAM 数据通路上。
其索引是 `{addr[16], addr[12:2]}`，tag 是 `{addr[24:17], addr[15:13]}`。
字加载会同时启动同步一拍的 cache 查找和投机 SRAM 请求；
命中时用 cache 数据回应，并取消尚在 SRAM 控制器等待队列中的请求，或抑制已经开始的 SRAM 读响应；
当前只有 `LD.W` 使用缓存命中和填充，`LD.B` 直接使用 SRAM 响应。
存储指令直接写穿，不做写分配，并使对应索引的缓存行失效。

SRAM 控制器的最短工作周期约为 `15 ns`，其中包含约 `3.5 ns` 的地址和请求输出、`10 ns` 的片上延迟、以及 `1.5 ns` 的结果读入。
当前在`191.7MHz`下一次`SRAM`访存需要 3 拍。读响应经过 4 项 FIFO 后按序返回，LSU 将读响应汇合后再送往 WBU；
写请求在 SRAM 周期结束时完成。

需要注意的是：当前 pending-store 队列尚未实现同址 store->load 的转发或阻塞检查，所以存在访存一致性的问题。

### 写回

ALU、MUL 和 load 的结果首先出现在 ALU、MUL、LSU 各自的写回端口上，供 BPU 和 LSU 旁路使用。
`B`、`BEQ`、`BNE` 以及目的为 `r0` 的 ALU/JIRL 指令也会经过 `XIU` 的结果缓冲和 `RRU` 的 `WBU`，只是不会写入寄存器堆。
store 不走这条寄存器结果通路，而由访存侧报告完成。

`RRU` 内的 `WBU` 按 `LSU > MUL > ALU` 每拍选出至多一项，先进入两项缓冲。
完成退休握手后，仅在 `prd != 0` 时写入物理寄存器堆并翻转写回状态，仅在 `old_wd != 0` 时把旧物理寄存器还给 `FLT`。
这里的“退休”指各结果的完成握手，不是 ROB 按程序顺序提交。

需要注意的是：当前代码还保留了一个边界问题：`RRU_WBU_ready` 被 `!FLT_full` 统一门控，即使队首结果的 `old_wd == 0`、不需要归还寄存器，也可能因自由表已满而停住。

## 决赛

决赛题目要求计算二进制点积：两个 32 位数 `X`、`Y` 按位展开为取值为 `+1/-1` 的向量，结果等价于 `32 - 2 * popcount(X ^ Y)`。

决赛程序（`asm/user-sample.S`）按 2 倍展开处理输入对，每对用一条 `mul.w` 作为计算原语：

```asm
_start:
    lu12i.w     a0, 0x1c200      // 输入起点
    lu12i.w     a1, 0x1c400      // 输入终点
    lu12i.w     a2, 0x1c400      // 输出起点
loop:
    beq         a0,a1,loopend
    ld.w        t0,a0,0x00       // 读入 4 对（8 个字）
    ld.w        t1,a0,0x04
    ld.w        t2,a0,0x08
    ld.w        t3,a0,0x0c
    ld.w        t4,a0,0x10
    ld.w        t5,a0,0x14
    ld.w        t6,a0,0x18
    ld.w        t7,a0,0x1c
    addi.w      a0,a0,0x20
    mul.w       s0,t0,t1         // 每对一次 mul，由硬件点积器给出结果
    mul.w       s1,t2,t3
    mul.w       s2,t4,t5
    mul.w       s3,t6,t7
    st.w        s0,a2,0x00       // 写回 4 个结果
    st.w        s1,a2,0x04
    st.w        s2,a2,0x08
    st.w        s3,a2,0x0c
    addi.w      a2,a2,0x10
    // 第二组相同的 18 条，再处理 4 对
    b           loop
loopend:
    lu12i.w     t0, 0x1f000
    ori         t1, zero, 0x7
    st.b        t1, t0, 0        // 自行发出结束令牌 0x07
    jirl        zero, ra, 0
```

由于测试框架不涉及 `MUL` 乘法，可以直接把乘法器改成上述点积器，在硬件上完成这一步运算。

计时上，用户程序在循环结束后自行向 UART 数据口（`0x1F000000`）写入结束令牌 `0x07`，再执行返回；
这是因为原始决赛程序遇到了和 Alpha 阶段一样的超时问题。

该修改配合 175 MHz 的频率，在 12 ms 内通过了对应的测试任务。

## 工具

以下简要列出本次竞赛过程中用到的工具及其用途：

1. **模拟器（`emu/`）**：为了在 RTL 之前验证汇编与 supervisor 功能，我撰写了一套 LA32R 指令步进模拟器，并把它作为 commit difftest 的黄金参考，其能够输出 commit 流与功能级 Konata 轨迹。
2. **Verilator（`sim/`）**：处理器设计完成到上板之间，用它做功能和性能验证：裸机四个 workload 回归、supervisor 端到端 UART 测试、`compare_commit.py` 逐提交比对和 `isa-decode-audit` 译码审计；同时它可以产生处理器的实际 Konata 轨迹。
3. **Konata**：波形可视化工具，把 `sim/KonataTrace.sv` 采样出的日志渲染成流水线视图，用于逐拍分析各测试的迭代与停顿。
4. **Vivado**：综合、实现与时序报告工具，用于查看 WNS 并生成 bit 流，扫频数据也由它得到。
5. **opencode**：AI 编程工具，能有效节省开发与调试时间。

## 想法

1. 龙芯杯个人赛的成绩只取决于复赛和决赛的测试用时
   1. 复赛的测试主要从指令供给、分支预测、访存压力三方面考虑：
      1. 双发射也许会更好，但是更难做更难调；单发射足够了
      2. 分支指令要么是简单的 `BEQ` 不跳、`BNE` 跳，要么是 MIXED 的数据相关分支。前者静态预测足够了，后者太难猜
      3. STREAM 和 CRYPTO 没有复用，缓存帮不上忙；MATRIX 和 MIXED 虽有复用，但是全部命中还是需要更好的时序优化。
      4. MIXED 这个测试太短，很难体现优化的差异性。
   2. 决赛的样例要么靠软件要么靠硬件；有必要为硬件优化预留空间
      1. `MUL` 作为一条必然很长的指令，很适合改成专门的指令
2. 综合脚本对时序的优化空间还很大：同一设计在不同频点跑实现时，个别高频点反而会收敛
   1. 可以配置并行化编译，同时给多个点跑编译，挑时序能过的频率最高的点
3. AI 确实能做很多：例如把 280 ms 优化到 229 ms，但是需要方向和准则。
4. FPGA比赛要熟悉FPGA芯片的特性：
   1. 善用distribute-RAM：可以多读一写的小容量存储器
   2. `15 ns` 的访存周期是在输入输出都打 `IOB` 寄存器的情况下确定的
